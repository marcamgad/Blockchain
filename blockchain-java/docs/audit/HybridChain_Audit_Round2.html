HybridChain Security Audit II

A second full pass over the HybridChain Java IoT blockchain, done after the first round of fixes. It covers every module, re-checks the earlier fixes, and records what was found and fixed in this round and what is still open.

Date 18 Oct 2026 Code blockchain-java, branch fix/audit-batch3 on top of c567794 plus this round's uncommitted changes Stack Java 17 · Spring Boot 3.5.16 · BouncyCastle 1.86 · LevelDB · Chicory WASM 1.0.0

1. Verdict

Ready for a private testnet or a supervised pilot. Not yet ready for production.

All 77 recorded findings were reviewed. Every critical finding is fixed, and each fix has a test that fails on the old code and passes on the new code. Production is blocked by three things: leader-failure recovery can stall, the system has never been run as a real multi-node network on separate machines, and the keys that were published in the repository have to be replaced.

3. Scope and method

The audit covered all 96 main source files (about 21,400 lines) and the 157 test files, plus the build file, Docker files, the compose files and the environment template. Modules were reviewed in risk order: transport and P2P, ledger, consensus, cryptography and storage, contracts, devices and identity, API and IoT ingress, privacy, AI, then operations.

Rules every fix followed

  • Each finding gets a test that asserts the correct behaviour. The test must fail on the old code before the fix counts. For example, the WASM metering test failed 3 out of 3 on the old engine, where the infinite loop ran the full 5-second timeout.
  • The full suite must stay green after every change. The audit proof suite runs with mvn -o test -Dtest=HybridChainAuditPoCTest -Daudit.excluded=none.
  • Fixes are defensive: they validate, bind or bound. No feature was removed without a replacement path. The old unsigned REST submission now answers 410 Gone and points to the signed endpoint.
  • Changes that alter consensus encodings are marked as such (see section 8).

5. This round's fixes

Fourteen findings were fixed in this round. They are listed with what happened before the fix and what happens now. Earlier rounds (HC-001 to HC-064) are summarised in the ledger in section 7.

CRITICAL

HC-046 · One leader signature finalised a block

consensus/PBFTConsensus.java · verifyBlock, verifyCommitCertificate, buildCommitCertificate · Block.java · PeerNode.java applyBlockAtSequence
Before

If a node had not seen the commit votes itself, verifyBlock accepted any block signed by the current leader. One validator was enough to finalise a block. Separately, the commit path applied the pending block even when no quorum hash existed at all. Blocks from earlier views were rejected, because only the current leader's key was tried, so a lagging node could not sync history.

After

Every block carries a commit certificate: the COMMIT signatures of the validators that voted for it. The signatures cover the block hash, and the certificate is not part of the hash. A block is final only if the proposer's signature verifies and either this node saw the quorum itself or the certificate holds valid signatures from 2f+1 distinct, known, non-slashed validators. A single-validator network is the exception, because there the quorum is 1. The commit path refuses a block when there is no quorum or the hash or height differs.

Proof: CommitCertificateTest. A second node that never saw the votes accepts a block with a 3-of-4 certificate. It rejects no certificate, 2 of 4, a duplicated signer, and a signature attached to the wrong validator. The existing BlockStructureTest case that applied a leader-only block in a 4-validator network is now rejected, as intended.

HIGH

HC-065 · Proposals were voted on without checking who signed them

Blockchain.java validateBlock · Consensus.verifyProposerSignature · PBFTConsensus
Before

validateBlock checked only that a signature was present. It is the only check a gossiped proposal gets before honest validators send PREPARE, so validators could spend votes on a block no validator had signed.

After

The proposer's signature is verified through the consensus engine. PBFT checks the proposal signature only, because a proposal has no certificate yet. PoA uses its own block signature format. Mocked engines in tests stub the new method.

Proof: CommitCertificateTest.proposalSignatureIsVerified.

MEDIUM

HC-066 · Vote signatures were ambiguous

PBFTConsensus.PBFTMessage.serializeForSigning
Before

The signed bytes were the string phase + view + seq + hash + id with no separators. View 1, sequence 23 and view 12, sequence 3 produced identical bytes, so one signature counted for both.

After

Votes are signed over a length-prefixed binary encoding with the domain tag HYBRIDCHAIN-PBFT-v2. Each field has a fixed position, and the domain tag separates votes from blocks and checkpoints.

Proof: CommitCertificateTest.voteEncodingIsUnambiguous.

HIGH

HC-068 · A node that fell behind never caught up

PeerNode.java broadcastPeerList, PEER_DISCOVERY handler, recordPeerHeight, BLOCKS_RESPONSE
Before

Peer heights were never recorded, because setBlockHeight was never called. Every peer looked like height 0, so the sync loop never requested a block. A node that restarted or missed a round stayed behind for good.

After

Each node's peer announcement includes its own height. Peer messages are signed, so a node can only report its own height. Heights are hints only: every block received through sync still goes through full validation and the certificate check, and a peer that sends a bad block loses score.

MEDIUM

HC-067 · Sync requests had no size limit

PeerNode.java REQUEST_BLOCKS and BLOCKS_RESPONSE handlers · MAX_SYNC_BATCH = 50
Before

The requesting peer chose the range, so a single request could make a node load and serialise its whole chain into one message. Responses of any size were also accepted.

After

Served ranges are clamped to at most 50 blocks the node actually has, starting at height 1 or later. Responses with more than 50 blocks are dropped, and the sender loses score.

HIGH

HC-064 · Anyone on the MQTT broker could control gateway-owned devices

api/AbstractIoTMessageAdapter.java submitDeviceTx, submitSignedTx · MQTTAdapter · CoAPAdapter
Before

A message on blockchain/iot/<device>/mgmt became a management transaction signed with the node's own key. Lifecycle checks compare the device owner with the transaction sender. On a gateway that owns its devices, anyone who could publish to the broker (default tcp://localhost:1883, usually with no login) could suspend, revoke or re-flash them, and each message also spent the node's fees.

After

The node never signs management actions on someone else's behalf. MQTT /mgmt only relays an IOT_MANAGEMENT transaction signed by the owner, and all the normal ledger checks apply. CoAP /tx uses the same relay, and its rate limit is now per sender instead of one shared counter.

Proof: IoTIngressTest, plus the updated HC-004 audit proof.

LOW

HC-063 · WebSocket topics and filters

api/EventBus.java
Before

Any topic name created a map entry that was never removed, so memory grew without limit. A session had one filter shared by all its subscriptions, so a second subscription silently replaced the first one's filter. A filter that could not be applied sent the event anyway.

After

There are six fixed topics. Each topic has its own filter, with at most 8 keys. An event that cannot be filtered is not sent.

LOW

HC-062 · Contract gas limit could overflow

Blockchain.java CONTRACT case
Before

fee * 1000 was computed without an overflow check, so a huge fee could wrap around to a negative or garbage limit.

After

The multiplication is capped instead of wrapping. WASM also has a hard 10M gas cap (HC-059).

HIGH

HC-071 · A published PUF proof could be reused with other readings

privacy/ZKProofSystem.java telemetryChallenge, OwnershipProof.createForTelemetry · Blockchain.java TELEMETRY validation
Before

The prover chose the challenge of a PUF device's ownership proof (the helper used the constant "TEST_CHALLENGE"), and the proof did not cover the payload. The proof is stored on-chain in the transaction data. Anyone could copy it into a new transaction with different readings, and it was accepted as coming from that device.

After

The verifier recomputes the challenge from the device ID, the relaying sender, the sender's nonce and the payload, under the domain HYBRIDCHAIN-ZK-TELEMETRY-v1, and requires an exact match. Each proof is valid for exactly one transaction carrying exactly that payload.

Proof: TransactionLifecycleTest.testTelemetryProofReplayRejected (payload swapped, and a different sender, are both rejected).

MEDIUM

HC-072 · The private-transfer nullifier could be anything

Blockchain.java PRIVATE_TRANSFER validation · ZKProofSystem.privateTransferChallenge, proofNullifier
Before

The nullifier was a free field next to the proof. A spent nullifier only stopped someone who reused the same value, so the double-spend check meant nothing. The challenge was not tied to the transaction either.

After

The proof must use the challenge derived from (sender, nonce), and the nullifier must equal the hash of the proof. Note that private transfers still move no value (see section 6).

LOW

HC-073 · A threshold proof without a commitment verified as true

ZKProofSystem.ThresholdProof.verify
Before

if (commitment == null) return true. A deserialised proof missing its commitment passed.

After

It now fails closed. The code documents that the eligibility gate is unsound by design and must stay disabled (see section 6).

MEDIUM

HC-074 · Firmware "verification" verified nothing

lifecycle/DeviceLifecycleManager.java updateFirmwareSigned, firmwareDigest · Blockchain.java UPDATE_FIRMWARE
Before

Any FirmwareProof whose hash matched the installed image counted as verified. Anyone could build one, because it is a commitment only the device secret can open. The on-chain action never passed a proof at all, so every legitimate firmware update cut the device's reputation by 20%.

After

An update is VERIFIED only if the device's trusted manufacturer signed firmwareDigest(deviceId, version, hash). The on-chain action takes an optional manufacturerSignature. A self-made proof, a signature from someone else, or a signature for another version is recorded as UNVERIFIED and penalised.

Proof: DeviceActivationTest.firmwareNeedsManufacturerSignature.

LOW

HC-069 and HC-070 · Checkpoint encoding and fast-sync checks

Checkpoint.computeCheckpointHash · Blockchain.init fast-sync branch
Before

The checkpoint hash was a bare concatenation with no domain, signed by the same keys as blocks and votes. Fast-sync loaded the UTXO set without comparing it to the checkpoint's utxoRoot, and never checked that the stored block matched the checkpoint's height, hash and state root.

After

The hash is length-prefixed with the domain tag HYBRIDCHAIN-CHECKPOINT-v2. Fast-sync rejects the checkpoint unless the block, the state root and the UTXO root all match. Checkpoints only come from the node's own encrypted storage, so this is defence against a corrupted or tampered disk.

HC-070 has no dedicated test yet. The existing checkpoint tests resume from the chain tip and never reach this branch.

MEDIUM

HC-077 · AI state was fed from unaccepted and unauthenticated data

Blockchain.java FEDERATED_UPDATE and TELEMETRY_BATCH cases
Before

Federated-learning updates went into the node-local manager inside the state transition. That transition also runs during block simulation and for rejected blocks, so updates were double-counted or came from blocks that never existed. TELEMETRY_BATCH carries no device signatures, yet it trained the anomaly detector, so any sender could shape any device's baseline.

After

Federated-learning updates are applied only after the block is accepted, on the live state. Batch readings no longer touch the detector. Only authenticated TELEMETRY from accepted blocks feeds detection.

HIGH

HC-075 · The environment template shipped usable keys

.env.example (repository root)
Before

The template contained a storage key and 20 node private keys derived from a seed written in the same file. Any network started from it had keys anyone could recompute.

After

Every value is blank, with instructions to run scripts/generate_keys.sh for each network. The old keys are in git history and must be treated as compromised.

LOW

HC-076 · The container ran as root

blockchain-java/Dockerfile
Before

The node ran as root inside the container.

After

The node runs as a dedicated system user hybrid that owns /app.

6. What is still open

These items are known and not fixed. Most need a design decision, not a patch. They are ordered by how much they matter for production.

#ItemRiskWhy it is open and what it needs
O-1No NEW_VIEW step in view changeHIGHSafety holds: a node never sends two COMMITs for one height, so two different blocks cannot both reach 2f+1. But if the leader fails after some honest nodes committed to a block, the next leader cannot learn that block, and the height can stall. The fix is the standard PBFT NEW_VIEW message, which carries prepared certificates into the next view so the new leader re-proposes the right block. This is a protocol change and needs its own design and fault-injection tests.
O-2No real multi-node deployment testHIGHEverything has been tested in one process, with in-memory networking. Nothing has run on 4 or more separate machines (for example Raspberry Pis) with real mTLS, real clocks and real packet loss. This is the gate for a production claim.
O-3Rotate the published keysHIGHAny key from the old .env.example, from the old KeygenTool default seed, or derived from a published seed is public. Generate fresh keys per network.
O-4HC-058 contracts read local sensorsMEDIUMThe bytecode and WASM sensor reads return each node's local hardware value. Today every node returns the same mock value, so nothing breaks. With real sensors, nodes would disagree. Contracts should read committed on-chain telemetry or a signed oracle value.
O-5Misbehaviour evidence is not on-chainMEDIUMDouble votes are detected and slashed locally (HC-019 removed slashing from the state transition so nodes cannot diverge). Penalising a validator network-wide needs an evidence transaction carrying both conflicting signed votes.
O-6Private transfers move no valueMEDIUMPRIVATE_TRANSFER checks the proof, takes the fee and records the nullifier, and that is all. Either build commitment-based balances, or mark the type disabled so nobody relies on it.
O-7ZK leader eligibility is unsoundMEDIUMThe prover picks the commitment, so the proof says nothing about the validator's real reputation. Eligibility is also kept per node, not agreed by consensus. The gate is off by default and must stay off until the protocol issues the commitment.
O-8Repository hygieneLOWLevelDB folders (blockchain-java/data/, data/chain-db.bak/), all of node_modules, and scratch files (Patcher.java, patch.py, logs) are committed. Untrack them and add them to .gitignore.
O-9Coverage gapsLOWStartup (com.hybrid.App) 0%, iot 0%, api 47%, branch coverage 60.6%. Also missing: a fast-sync load test (HC-070) and a PeerNode-level sync test (HC-067, HC-068).
O-10Smaller itemsINFOGovernanceManager is unused dead code. spring-webmvc 6.2.x has two advisories that only Spring 7 fixes, for features this node does not use. MQTT and CoAP have no TLS (DTLS) of their own. Device revocation has no admin or recovery path.

8. Upgrade and rollout

This round changes three signed encodings: PBFT votes (v2), checkpoint hashes (v2) and block validity (a commit certificate is required). Nodes on the old code and nodes on the new code cannot agree. Upgrade every validator at once, and start test networks from empty storage.

Before any network start

  • Generate a fresh key set for each network with blockchain-java/scripts/generate_keys.sh, and keep it in .env, which must never be committed.
  • Set NETWORK_CA_SEED and VALIDATOR_PUBKEYS for at least 4 validators. Keep DEBUG=false outside development.
  • Secure the MQTT broker (authentication and TLS), because device payloads travel over it in plaintext otherwise.
  • Device tooling that sends management actions over MQTT must now send a transaction signed by the owner. Firmware tooling should attach the manufacturer's manufacturerSignature.

Repository cleanup (run once, then commit)

git rm -r --cached blockchain-java/data data/chain-db.bak node_modules
git rm --cached blockchain-java/Patcher.java blockchain-java/patch.py blockchain-java/tmp-failures.txt

Then add those paths to .gitignore. Removing them from history as well needs a separate history rewrite, like the one already done for commit trailers.

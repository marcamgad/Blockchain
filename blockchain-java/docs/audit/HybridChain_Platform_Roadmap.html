HybridChain Platform Roadmap

What HybridChain would need to work as a public cryptocurrency and as a general-purpose smart-contract platform, measured against the 2025 to 2026 state of the art and mapped to this codebase.

Date 21 Oct 2026 Baseline HybridChain after audit round 2 (695 tests passing, 78 findings fixed or tracked) Companion HybridChain Security Audit II

1. Summary

HybridChain is a solid permissioned IoT chain. A public coin needs four foundations it does not have yet: divisible money, proof-of-stake, Ethereum-compatible execution and light clients.

The audit fixed the safety problems, so the core now behaves like a correct permissioned BFT chain. A public cryptocurrency is a different trust model. Anyone can join, value is at stake, and wallets, exchanges and bridges must be able to integrate. Four changes alter the protocol itself and should be made before any coin is launched, because changing them afterwards means a hard fork with real money on it:

  • Money units. The supply is 21,000,000 indivisible units and the reward is 50 units. The coin needs decimals.
  • Who may validate. The validator list is fixed today. An open network needs stake-weighted validators, with unbonding and slashing.
  • Addresses and signatures. Addresses need checksums, and signatures need a versioned post-quantum path.
  • Verifiable headers. The commit certificate added in round 2 is the basis for light clients, but it needs compact aggregate signatures and validator-set change proofs.

Recommendation: keep HybridChain's IoT identity layer as the reason the chain exists, and become Ethereum-compatible by embedding a proven EVM. Build the rest by reusing audited libraries instead of writing new cryptography. Section 4 compares this with the two alternatives.

This is engineering research, not legal or investment advice. Issuing or offering a token to the public is regulated in many places (section 3.13). Have a lawyer check the plan before any public sale or listing.

3. Gaps against the state of the art

Each area lists what HybridChain has, what current systems do, and what to build here. Throughput and latency figures from papers and vendor blogs are self-reported benchmarks and are cited as such.

3.1 Money: units, supply and issuance

FOUNDATION
HybridChain today

21M indivisible units, a 50-unit reward halving every 210,000 blocks, and a minimum reward of 1. Amounts are Java long.

State of the art

Bitcoin divides a coin into 10⁸ units and Ethereum into 10¹⁸. Proof-of-stake chains pay validators through issuance plus fees, often with a burn (Ethereum since EIP-1559) to offset inflation.

Build here
  • Define 1 coin = 10⁸ base units. 21M × 10⁸ = 2.1 × 10¹⁵, which fits in a long (max about 9.2 × 10¹⁸). Keep Math.*Exact everywhere.
  • Replace halving with a staking-rate-based issuance curve once proof-of-stake exists. Keep the base-fee burn.
  • Fix the genesis allocation and vesting in the genesis file, never in code.

3.2 Who may validate: proof-of-stake

FOUNDATION
HybridChain today

A fixed validator list and one vote per validator. Equivocation evidence jails a validator on-chain, but there is no stake to slash.

State of the art

Bonded stake gives voting power, and misbehaviour burns part of it. The unbonding period is kept longer than the window in which evidence can be submitted, so a validator cannot leave before being punished. New or long-offline nodes start from a trusted recent checkpoint (weak subjectivity) to stop long-range rewrites by validators who have already left.

Build here
  • Transactions to bond, unbond, delegate and withdraw. Stake held in the state root.
  • Validator set changes only at epoch boundaries, decided by state.
  • Quorum by stake (more than 2/3 of voting power) instead of by head count, in PBFTConsensus.quorumSize and certificate checks.
  • Evidence burns a share of stake, and part of it goes to the reporter. Reuse EQUIVOCATION_EVIDENCE.
  • An unbonding period longer than the evidence window, plus weak-subjectivity checkpoints for new nodes (the checkpoint code exists).

3.3 Consensus performance

IMPROVE
HybridChain today

Classic PBFT with all-to-all votes, O(n²) messages per block. One ECDSA or ML-DSA signature per vote in each certificate.

State of the art

Linear or pipelined BFT (the HotStuff family) and DAG-based protocols. Mysticeti reports about 0.5 s WAN commit latency, but a follow-up paper measured large slowdowns under Byzantine faults. Raptr (Aptos, 2025) reports 260,000 TPS with sub-second latency on 100 replicas. These are the authors' own benchmarks.

Build here
  • Keep PBFT while the network has fewer than about 50 validators. It is simple and now correct.
  • First win: BLS aggregate signatures in certificates. One constant-size signature plus a signer bitmap makes certificates small enough for light clients and bridges. Use the IETF BLS draft with proof-of-possession against rogue keys.
  • Then separate data dissemination from ordering (Narwhal-style batches) before considering a DAG protocol.
  • Extend the TLA+ model to commit safety and NEW_VIEW before each change.

3.4 Execution: smart contracts for general use

IMPROVE
HybridChain today

A custom stack VM plus WASM (Chicory), executed one transaction at a time. Gas is now deterministic.

State of the art

EVM compatibility gives access to wallets, Solidity and audit tools. Parallel execution comes in two forms: Block-STM runs transactions speculatively and rechecks them in a fixed order, so results stay deterministic (the paper reports up to 170k tps in benchmarks, and much less under contention). Sui instead uses an object model in which owned-object transactions skip full consensus.

Build here
  • Embed a proven Java EVM instead of writing one. Hyperledger Besu is Java and publishes its EVM as a library. Keep WASM for IoT-specific contracts.
  • Add an Ethereum JSON-RPC endpoint (eth_*) so MetaMask, ethers.js and indexers work unchanged.
  • Add Block-STM-style parallel execution only after the EVM, behind a test that compares its results with sequential execution.
  • Fix HC-058 first: contracts must read committed telemetry, not each node's local hardware.

3.5 State storage, sync and light clients

IMPROVE
HybridChain today

A Merkle-Patricia trie for accounts, with the other state hashed in beside it. Fast-sync only from local storage. Account proofs exist.

State of the art

Storage built for Merkle proofs: QMDB (2025) reports millions of state updates per second, as the authors' own benchmark. Ethereum's EIP-7864 drafts a unified binary trie, which its researchers describe as years away. Light clients follow block headers plus aggregate signatures. Zero-knowledge VMs can now prove whole blocks: Succinct reports proving 99.7% of Ethereum blocks in under 12 s on 16 GPUs (a vendor claim).

Build here
  • Snapshot plus chunked state download from peers, each chunk verified against the certified state root.
  • A light-client protocol: headers, BLS certificates and validator-set change proofs. This is also the base for bridges.
  • Fold all state (devices, DIDs, nullifiers, the jailed set, later stake) into one authenticated tree, instead of extra hashes next to the trie.
  • Consider ZK proofs of state transitions later, for very light IoT clients.

3.6 Accounts, addresses and wallets

FOUNDATION
HybridChain today

Addresses are a 20-byte hash in lowercase hex, with no checksum. Keys are raw. A transaction carries a network ID (replay protection exists).

State of the art

Checksummed addresses: Bech32m (BIP-350), or EIP-55 if EVM-style. Seed phrases and key derivation: BIP-39 and BIP-32/44. Account abstraction: Ethereum's EIP-7702 (live since Pectra, 7 May 2025) lets an ordinary account run smart-account code, which enables batching, sponsored fees and key rotation.

Build here
  • Bech32m addresses with the human-readable prefix hb (or EIP-55 if fully EVM-native).
  • Register a SLIP-44 coin type and support BIP-39/32/44 using an existing library (web3j or bitcoinj), so hardware wallets can be added.
  • Native multisig and key rotation at account level. The multisig manager exists but is not part of the account model.

3.7 Cryptography and the post-quantum path

AHEAD
HybridChain today

secp256k1 ECDSA (low-S, full digest) and ML-DSA, domain-separated hashing and AES-GCM with AAD.

State of the art

ML-DSA is the common default. FN-DSA (Falcon) is smaller (about 666 bytes against about 2.4 KB) but harder to implement safely. SLH-DSA is conservative but large (about 7.9 KB). Bitcoin is discussing BIP-360. Ethereum is moving consensus toward hash-based signatures and leaving accounts signature-agnostic through account abstraction. Statuses are still changing.

Build here
  • A versioned signature-scheme ID on every key and signature (crypto agility), so a scheme can be added or retired by a planned upgrade.
  • A hybrid mode (ECDSA and ML-DSA together) for high-value accounts and validators.
  • Price signature bytes in fees. ML-DSA signatures are about 30 times larger than ECDSA ones.
  • Keep BLS for vote aggregation (not post-quantum). Plan a later post-quantum aggregation scheme.

3.8 Fair ordering and MEV

LATER
HybridChain today

The leader orders transactions by fee. That is harmless for telemetry, but it lets the leader front-run trades once DeFi exists.

State of the art

Threshold-encrypted mempools hide transactions until their order is fixed. Shutter runs on Gnosis Chain. A 2026 survey and a 2025 security analysis both show the designs are still maturing, with known front-running gaps in some integrations.

Build here
  • Not needed for launch. Revisit when DEX or lending contracts appear.
  • A cheap first step: deterministic ordering rules inside a block that every validator checks.

3.9 Bridges and interoperability

MISSING
HybridChain today

Anchoring is simulated, and no bridge exists.

State of the art

Bridges verified by light clients (IBC-style), or by ZK proofs of the other chain's consensus. Bridges secured by a multisig of trusted operators have been the most-attacked part of the ecosystem.

Build here
  • Remove or clearly mark the simulated anchoring until it really sends.
  • After light clients exist: a light-client bridge to Ethereum. Don't launch a multisig bridge.

3.10 Privacy

DECIDE
HybridChain today

PRIVATE_TRANSFER moves no value. The ZK leader-eligibility gate is unsound and must stay disabled.

State of the art

Shielded pools with note commitments, nullifiers and SNARK proofs (Zcash Orchard style), or proofs generated in a general-purpose ZK VM. Privacy coins face listing and compliance pressure in several markets.

Build here
  • Disable PRIVATE_TRANSFER at the protocol level until a real shielded design exists.
  • Keep privacy for IoT data (encrypted telemetry with selective disclosure), where it is most useful and least controversial.

3.11 IoT and DePIN: the differentiator

STRENGTH
HybridChain today

Device DIDs, manufacturer attestation, PUF identity, device-signed readings bound to their transaction, and federated learning with integrity checks.

State of the art

DePIN networks such as Helium, IoTeX and peaq pay devices for physical work. IoTeX's ioID registers and binds device identities to verify their data. Helium reports about 962,000 hotspots. Market-size figures vary widely between sources.

Build here
  • Hardware roots of trust (TPM or secure element attestation) next to PUF.
  • A sensor oracle: committed, device-signed telemetry that contracts can read. This also fixes HC-058.
  • Proof-of-physical-work rewards that only count authenticated readings. Never count unsigned batches (see HC-077).

3.12 Protocol upgrades and governance

FOUNDATION
HybridChain today

Rule changes (vote encoding v2, certificates, evidence) need every node to switch at once from empty storage.

State of the art

Named forks with activation heights (Ethereum's Pectra on 7 May 2025, then Fusaka with PeerDAS on 3 Dec 2025), a protocol version in each block, and on-chain parameter governance.

Build here
  • A fork schedule: ruleset(height) chooses the validation rules, so old blocks keep validating under old rules.
  • A protocol version in the block header.
  • On-chain governance of parameters by stake, after proof-of-stake exists. Delete or wire up GovernanceManager.

3.13 Regulation (EU example)

LEGAL
Why it matters

A coin offered to the public, and the exchanges and custodians that handle it, fall under financial rules in many countries. The EU's MiCA is the most complete example.

What applies (secondary sources, verify)

MiCA's stablecoin rules applied from 30 June 2024 and its service-provider (CASP) rules from 30 December 2024, with national transition periods ending by 1 July 2026. Public offers need a crypto-asset white paper. The Transfer of Funds Regulation (the travel rule) makes service providers pass sender and receiver information.

Do
  • Get legal advice before any token sale, listing or stablecoin.
  • Design so protocol and service provider stay separate. Nodes should not custody user funds.
  • Plan the white-paper content (rights, technology, risks) from this roadmap and the audit.

3.14 Security programme for real value

EXTEND
HybridChain today

Two internal audit rounds, 695 tests, 30 proof tests, CodeQL scanning and a TLA+ model of leader selection.

Expected for a public coin

Independent audits of consensus, cryptography and the EVM integration. Formal models of safety-critical protocols. Continuous fuzzing, an incentivised testnet, a bug bounty, reproducible builds, validator key management (HSM or remote signer) and an incident plan.

Build here
  • A remote signer for validator keys with protection against double signing.
  • Fuzzers for block, transaction and P2P decoding. A differential test of the EVM against Besu's reference test suite.
  • A multi-machine testnet with fault injection (audit item O-2).

4. Three ways to get there

A. Evolve HybridChain (recommended)

Keep the Java node and the IoT identity layer. Add proof-of-stake, BLS certificates, an embedded EVM, light clients and wallet standards from audited libraries.

For: keeps the differentiator and the audited core, and the codebase stays one language.

Against: the most engineering. Every consensus change needs proofs, models and audits.

B. Rebuild on an app-chain framework

Run the IoT modules on a mature framework such as Cosmos SDK with CometBFT, which brings staking, slashing, IBC and light clients.

For: the battle-tested parts arrive ready.

Against: a rewrite in Go, so the Java code and much of its audit evidence are lost.

C. Become a rollup or a token on Ethereum

Issue the token on Ethereum or an L2, and keep HybridChain as a permissioned IoT data chain that anchors to it.

For: the fastest and safest route to a liquid token. Security is inherited.

Against: HybridChain stops being the currency's chain, and fees and governance follow the host.

Option A fits the stated goal of one chain for currency, IoT and other uses, and builds on the work already done. Option C is the low-risk fallback if the team is small. A middle path also works: launch the token through option C while option A matures, then migrate.

5. Phased plan

The phases are ordered so each one depends only on earlier ones. Phase 1 changes the protocol, so it must be finished before any coin exists.

  1. Phase 0 · Finish the pilot

    Close the audit's open items

    • A multi-machine testnet with fault injection (O-2), and rotation of every leaked key (O-3).
    • Sensor oracle (HC-058 / O-4), disabling PRIVATE_TRANSFER (O-6), and removing or marking the simulated anchoring.
  2. Phase 1 · Currency foundations (protocol-changing)

    Make it money

    • Base units with 10⁸ decimals, plus a genesis file for allocations.
    • Bech32m addresses, BIP-39/32/44 wallets and a SLIP-44 coin type.
    • Proof-of-stake: bonding, delegation, epochs, stake-weighted quorum, stake slashing through the existing evidence transaction, an unbonding period and weak-subjectivity checkpoints.
    • BLS aggregate commit certificates with proof-of-possession.
    • A fork schedule and a block protocol version.
    • TLA+ models for commit safety, NEW_VIEW and stake changes.
  3. Phase 2 · General-purpose platform

    Make it programmable

    • Embedded EVM, Ethereum JSON-RPC and EIP-55 compatibility. Keep WASM for IoT contracts.
    • Light-client protocol, peer state snapshots and a unified authenticated state tree.
    • Native multisig and account abstraction, and versioned signature schemes with hybrid post-quantum accounts.
  4. Phase 3 · Scale and connect

    Make it fast and connected

    • Block-STM-style parallel execution, checked against sequential results.
    • Data dissemination separated from ordering. Evaluate HotStuff or DAG protocols with the formal model.
    • A light-client bridge to Ethereum, and DePIN rewards for authenticated physical work.
  5. Phase 4 · Launch readiness

    Make it trustworthy

    • Independent audits, fuzzing, an incentivised testnet, a bug bounty, a remote signer for validators and an incident plan.
    • A legal review of the token, white paper and service-provider boundaries before any public offer.

6. Rules for the build

  • Reuse audited libraries for cryptography. Use BouncyCastle (already used), a maintained BLS library, and BIP-39/32 from web3j or bitcoinj. Never hand-write pairing or lattice code.
  • Every consensus rule depends only on chain data. The audit's recurring bug class was node-local state leaking into validity: AI detectors, local slashes, wall-clock timeouts and local sensors.
  • Every encoding that gets signed is versioned and domain-separated. Round 2 had to fix four ambiguous encodings: votes, checkpoints, credentials and proof challenges.
  • Every change starts with a failing test, as in both audit rounds, and every protocol change also starts with a model.
  • Protocol changes go through the fork schedule once it exists, never through a coordinated restart.
